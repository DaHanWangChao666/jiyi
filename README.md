### 1. 🔴 8 张高阶术法牌：抽得到，打不出去

`cards.js` 第 18 轮新增的 8 张「筑基以上专属招式」，
**全部漏写在 `data.js` 的 `G.TECHNIQUES` 表里**。

而战斗界面渲染招式按钮时是这样筛的（`ui.js:827`）：

```js
const techs = Array.from(new Set(deck)).filter(n => G.TECHNIQUES[n]);
```

**没进 `G.TECHNIQUES` = 这个按钮永远不会被画出来。**

| 死牌 | 品阶 | 卡面承诺 |
|---|---|---|
| 寒渊剑诀 / 五岳剑气 / 雷符 / 万符归阵 | 良·玄 | power 24~40 |
| 夺元掌 / 化血神功 / 铁布衫 / 金刚不坏 | 良·玄 | power 22~44 / ward 40~70 |

**为什么测试没抓到：** `smoke.js` 只检查「事件引用的卡存不存在」，
不检查「术法牌有没有招式定义」；`verify-combat.js` 只用 `剑气纵横` 测招式。

**已修**：补上 8 条 `G.TECHNIQUES`，并把卡面一直写着、引擎从没读过的
`cost:{stone, life}` 也接通了（现在界面会显示成本，付不起会灰掉）。

### 2. 🔴 卡牌的「常驻战力 / 护体」在战斗里不算

`combatStats()`（战斗数值的**唯一**出口）只读 `attrs()` 和 `meta.up`，
**从不读 `agg().power` / `agg().ward`**。

实测（`dev/dbg-effects.js`，修复前）：

```
空牌组                   ： 气血 180　普攻 21　招式 32　护体 3
加【一剑破万法】(power 44)： 气血 180　普攻 21　招式 32　护体 3   ← 完全没变
```

受影响的**功法/法宝 33 张**，白写数值合计 `power 321`、`ward 248`。

**已修**：`power` → 伤害**乘数**（上限 ×2），`ward` → 受伤**百分比减免**（上限 35%）。
为什么用乘算不用平加：战力随境界线性涨、敌人 HP 随境界指数涨，
平加会让「吃卡」在后期变成噪音。现在一套剑修装 = 招式威力 **×2.99**。

> 顺带发现：`hpMul`（不坏金身诀 / 龙骨脊 / 山岳印）也是死的，一并修了。

### 3. 🟠 六个流派套装，四个半只生效

`setBonus()` 收集得很漂亮，然后**收集完就扔了**。
修复前，以下 11 个字段**全项目零读取**：

```
techMul  critSet  hpSetMul  dmgTakenSet  pillSetMul
setKarma  setAttr  wardPerRound  wardHold  pillChance  karmaPerAction
```

最伤的是**剑冢遗风**：界面明写「剑系招式伤害 +50%」，
凑齐三件法宝费半天劲，**伤害数字一动不动**。
这骗的是玩家的投入——比没有这个套装更糟。

**已修**：11 个字段全部接通。验收实测：

| 套装 | 招式威力 | 气血上限 | 受伤 | 其他 |
|---|---|---|---|---|
| 剑冢遗风 | 139 → **276** | 910 | — | 招式 +50%、重击 +10% |
| 符阵相生 | 138 → 149 | 895 | — | 护体不衰减 ✅ |
| 丹火不熄 | 138 | 903 | — | 丹药 ×2、产丹 25% ✅ |
| 夺道之痕 | 141 → 151 | 954 | — | 业障 +1/行动 ✅ |
| 不坏之身 | 140 → 184 | 1003 → **2107** | **×0.80** | |
| 中庸之道 | 140 → **222** | 937 → 1225 | — | 全属性 +12 |

> 「不坏之身」原本套装写 `hpMul:0.4`，而它的三张卡自己也带 `hpMul`（0.15/0.2/0.35）。
> 两个都接上后会变成 **×2.9 气血、直接无敌**，所以我把套装那部分降到 0.12，
> 让界面承诺的「+40%」量级与玩家实拿到的相符。

### 4. 🟠 业障根本不累积：夺道流的核心代价不存在

`engine.js:415-419`（修复前）：

```js
const kp = a.karmaPer;
if (kp>0 && (kind==='cultivate'||kind==='explore')){
  s.karma = clamp(s.karma + 0, 0, 30);   // ← + 0，这是一段空操作
}
```

实测：带 `karmaPer: 8` 的【吞天魔功】修行 10 次，业障 `1 → 1`。

**后果**：设计文档说夺道流「涨得最快，代价是**业障翻倍**→ 心魔必现」——
**涨得最快是真的（`cultFlat` 生效），代价是假的。**
夺道流曾是**纯收益、零代价的最优解**。

**已修**：现在只要身上带着任何「损阴德」的东西，行动就积业障。
刻意做了两处收敛，避免一局直接暴死：
- 按「件数」算，不按 `karmaPer` 点数叠加（点数差别只体现在渡劫判定与招式自带业障上）
- 只在**修行 / 探索 / 宗门事务**上积，静养养身不积

验收：一整套夺道装修行 20 次，业障 `3 → 30`（上限），
**约 15 次行动就把天谴招来**。这就是设计文档想要的「代价」，
但速率请你过目——如果你觉得太急，改 `engine.js` 里 `perAction` 的系数即可。

### 5. 🟠 73 档境界 vs 166 个事件（**待你拍板**）

复刻浏览器 `afterActionFlow` 的真实流程跑 60 局：

```
平均行动 272 次　平均最终境界：渡劫
平均遇到事件 80.5 个，其中不重复的只有 42.9 个
全程 73 档，平均每档 3.7 次行动、1.10 个事件
```

| 大境界 | 小层数 | 每层行动 | 每层事件 | 专属事件数 |
|---|---|---|---|---|
| 炼气 | 9 | 4.1 | 1.19 | **54** |
| 筑基 | 9 | 2.9 | 0.84 | **40** |
| 金丹 | 9 | 3.8 | 1.14 | 9 |
| 元婴 | 9 | 3.8 | 1.09 | 7 |
| 化神 | 9 | 2.1 | 0.69 | 9 |
| 炼虚 | 9 | 2.1 | 0.57 | **5** |
| 合体 | 9 | 1.9 | 0.60 | **5** |
| 大乘 | 9 | 1.5 | 0.50 | **5** |
| 渡劫 | 1 | 71.5 | 20.98 | **5** |

**问题不是「每档太快」，是「每档太像」**——1 个事件就跨一层，突破没有重量。
而且**筑基一档的事件（40）比合体+大乘+渡劫加起来（15）还多两倍多**：
炼虚之后 9 层小境界只有 5 个专属事件，其中 3 个还只能看一次。

这正是 `DESIGN.md §14.8` 自己记下的「`actsPerRealm = 40` 是个虚数」。
**它不是 bug，是两个方向没拍板。**

### 7. 你问的「渡劫」：它存在，但它不是一个地方

| 事实 | 数据 |
|---|---|
| 境界总档数 | **73 档**（8 个大境界 × 9 小层 + 渡劫 1 档） |
| `MAJOR_DEFS` 只定义了 | **8 个大境界**（渡劫不在里面） |
| 渡劫怎么来的 | `realms.js` 末尾**单独 push** 的一档，`major=9, sub=0` |
| 走到渡劫需要 | **72 次突破** |
| 实测到达率 | **100%**（60 局模拟全部走到） |
| 到了之后 | 突破按钮变成「雷 池 已 渡」且**禁用**，没有任何后续内容 |
| 结局列表里有「飞升」吗 | **没有**（life/slay/karma/ascend/sit/sect/sanxiu/world/hidden） |

所以 **100% 的一局最后都停在渡劫**，然后继续点到寿元耗尽——
**结局永远是「寿元耗尽」**（60 局 100%）。

`README.md` 和 `DESIGN.md` 把渡劫写成了重头戏（「要么被献祭，要么去献祭别人」、
真 Boss 是上一个走到渡劫的人）——**但那一章还没做。**

> 📌 **渡劫现在只是一个「最高的数字」，不是一个「地方」。**
> 这是 V0.2+ 最大的一块内容缺口。

### 顺手修掉的一个「测试自己的 bug」

`playthrough.js` 的「渡雷池诊断」**永远输出 0 局**，看起来像「筑基不可达」。
实际是它自己的统计 bug：`ascAttempt` 只在 `if(st.canAscend)` 分支里赋值，
而 `doBreak()` 会自己把 boss 交给调用方，所以那条分支很少走到。

**这个误导性输出很危险**——我一开始就被它骗了，以为筑基是死路。

### 还修掉了模拟器的一个「假设」

`smoke.js` / `playthrough.js` / `balance-events.js` 的战斗循环都是：

```js
if (techs.length){ E.useTechnique(techs[0]); acted = true; }   // 假设招式一定成功
```

招式接上材料成本后，模拟玩家会**死盯着一张付不起的牌反复尝试**——
既不推进回合也不掉血，300 次迭代后超时判负。
真玩家不会这么打，所以这是模拟器的锅，已改成「失败就换下一张，最后退回普攻」。

> 这也是修完之后 `smoke.js` 里「走到渡劫」的比例
> 从 **93.5% → 46.0%** 的原因：以前它没真的打渡雷池那一仗。

## 第四部分：留给下一轮的

1. **难度偏低**：随机策略很容易走到渡劫。寿元是唯一约束，但太宽松。
2. **`G.CURVE.actsPerRealm = 40` 是虚数**：设计说「一个境界 40 次行动」，
   实测 **3.7 次**。要么改常数，要么让修炼重新变得重要——**需要你拍板**。
3. **渡劫那一章还没有**：它是全游戏的终点，现在只是个数字。
4. **后四个大境界的事件各只有 5 个**：炼虚之后 9 层小境界靠 5 个事件撑。
5. **石头的消费口是平的**：`a.gainStone(120)` 在渡劫期约等于没有。
6. **`powerHint()` 是死代码**（`ui.js:454`），可以删。
